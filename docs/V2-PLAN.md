## 开发顺序和交付点

1. **M1：共享会话完成一个真实文档任务。** V2-01、V2-02 的可执行接续基础、V2-03
   和 V2-08 的现有范围。先选择已有文档操作，打通 UI/终端/审批/原位修改/回读。
   优先完成一条完整链，再扩范围；不反复研究所有潜在协议。
2. **M2：常见富编辑任务完成。** V2-04、V2-05、V2-06、V2-07、V2-08。
   按对象族推进，每族支持一组可组合的操作，不按“标题居中”等用户场景逐个造工具。
   Word、Excel、PPT 各准备一组混合格式任务，核对原位效果和恢复。
3. **M3：复用、体验和效率收敛。** V2-09、V2-10、V2-11、V2-12。
   Claude 适配独立推进；一个成熟适配器先完成一个运行器，再扩展其他。
4. **M4：冻结发布候选。** V2-14，回归 M1-M3 已交付范围，验收干净源码与安装包，
   公开说明尚未支持项。V2-13 材料齐全的子项可加入，没有材料则保留下一里程碑。

M1-M4 可分别形成预览版本。最终版本号在冻结范围时确定；不会把规划自动当作已实现。

## 困难部分的实现方向与止损点

| 难点 | 当前依据与拟定方向 | 第一项能判定路线的验证；失败后的处理 |
| --- | --- | --- |
| Codex 共享会话工具与审批 | 本机0.159.2生成协议含 thread/start.dynamicTools、带 threadId/turnId/callId 的动态工具请求和结构化响应。优先做薄桥，把 office_live/office_file 接到同一文档执行层；参数、授权和结果沿用现有定义 | 一次只读调用、拒绝一次写入、批准一次指定范围修改；真实 TUI/UI 都能收到结果，工具调用只执行一次。需要实测请求归属及恢复后的工具注册；若动态请求分发不可靠，验证会话级 MCP 配置作为替代，不并行发展两套运行器 |

## 防止重复踏步的执行约定

- 复用评估要给出结论：现成能力、实际缺口、选择的接口和下一步代码修改。
  一个探索完成后立即转实现或记录明确的受限证据；连续同类失败两次后换诊断方法。
- 每次推进围绕“一个可完成的用户任务”，同时完成工具接入、界面、运行和验收。
  不用测试数量、监听端口、接口存在代替功能闭环。
- 维护对象/操作矩阵：已实现、已实测、受限、待实现。旧证据保留，只补新增或受影响检查。
- 检查必要的权限、目标、版本和恢复；复用现有保护，不为每个小操作另起审批/状态系统。
- 发现技术限制时记录复现、来源、影响和替代方案；没有证据时不称为产品做不到。
- 大块任务难以一次完成时拆成交付点。调整正式范围要写明移走的任务，避免半完成后改称完整。
- 开发仍在原 workbench 目录；发布 Git checkout 在 PROGRESS.md 中记录。单次组件更新、
  功能变更与发布包各有对应提交和证据，保持可追溯。
